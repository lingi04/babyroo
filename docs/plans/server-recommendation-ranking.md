# Recommendation ranking for the eight-question flow

## Plan and decisions

- Keep the existing questionnaire and recommendation cards. Submit and persist the existing interest answer as an optional, validated preference. Missing and neutral values give no ranking boost.
- Recommend up to three eligible outings that suit every selected child when shared outings exist. This also preserves the existing result limit for a single selected child. Use individual recommendations only when the eligible inventory contains zero shared outings.
- In the individual fallback, choose up to one suitable outing per selected child. Show the matches available for the original dates. If an outing is chosen for multiple children, show it once and explain who it suits using the existing reasons area. If one child has no eligible match, return the matches for the other children. A session with zero matches uses the existing empty outcome and costs zero credits. There is no date-broadening flow.
- Assume the nearest-outing answer favors the same district where known, with geographic alternatives still eligible. Reasons can name the district match. Distance, travel time and convenient transit require supporting facts. Keep price, reservation preference and indoor or outdoor preference as ranking signals. Closed bookings remain ineligible.

## Implementation

### Explaining visit-date age on result cards

- Whenever a result uses age on a prospective visit date, put the date used and the child's completed age in months in the first line of the existing `추천 이유` area. Use conditional Korean so parents understand the assumed visit date. For example, `11월 28일에 방문한다면 하윤이가 24개월이 되어 참여할 수 있어요.`
- For a range or flexible request, use the earliest supported date on which the outing meets the relevant children's age limits as the example date. Where a birthday limits the eligible dates, also give the applicable window. For shared outings, identify each child and age as of the same date. For individual outings, name the corresponding child. When one card covers siblings on different dates, give each child a separate date and age.
- Compose this explanation on the server from the selected child snapshot and the same date and age calculation used for eligibility. Persist it with the result so history shows the original explanation. Keep nicknames within Babyroo when composing the final copy. Only show the notice when the session contains evidence for the calculation.
- Verify both engines return the notice for a single child, siblings on a common date, a birthday inside the window and different per-child dates on a merged card. Verify a reopened session displays the original ages after a birthday. Inspect the proposed copy in the current card at phone size during UI plan review before implementation.

Main agent implements after plan approval. Use the existing session and result contracts and reuse the existing event query and response parser where they support the behavior.

1. Carry the interest enum through app request serialization, session preferences, history and retries. Preserve old sessions that have no interest and retain the single submitted interest as a session-level preference.
2. Resolve the visit window using the request date in `Asia/Seoul` with parity to the app. Compute eligibility using event date overlap, booking status, and documented age bounds per selected child. Find shared versus individual mode before truncating results. Apply date filters and paginate or otherwise examine eligible inventory upstream of the current 300-item fetch limit. Prevent the provider's shortlist limit from suppressing a shared match or dropping an otherwise covered child.
3. Make both server recommendation engines use the same eligibility and coverage rules. Rank eligible options using known practical fit, then supported interest and the selected short-duration or activity preference. Keep a deterministic scorer as the baseline, with catalog order used only to break ties and unknown price receiving no affordability boost.
4. Keep one model call per request with eligible candidates. Project only candidate facts, normalized preferences, ages and coarse departure area. Use session-local labels where the model needs to distinguish children. Validate model choices against each eligible set. In individual mode, use deterministic eligible picks to fill any child omitted by an otherwise usable model response. Include a short, factual Korean explanation for each result using the existing reasons area. Replace full prompts, responses and provider errors in logs and stored errors with sanitized metadata. Preserve the existing credit rules for successful and failed sessions.

## Acceptance and verification

### Independent review decisions

- Resolve selected IDs against the session snapshot, deduplicate IDs and handle missing children explicitly. A missing snapshot cannot establish that an outing fits the whole group. Preserve supported legacy requests without child information as general recommendations with age suitability unknown.
- Calculate completed months using calendar-valid birth dates. Reject invalid or future birth dates as evidence of age eligibility. Use the request date for interpreting the questionnaire. The proposed attendance-date policy below governs event eligibility.
- Carry a session-local child assignment in the internal result processing. Validate each choice against the server's eligible set before merging duplicate event IDs. Build the child-specific Korean reason from the verified assignment on the server. The public result shape already supports it. The app renders every returned card and its reasons. Apply the shared limit of three only in shared mode, including in the provider schema and parser. Reserve deterministic picks for children beyond the provider shortlist budget.
- A flexible or missing visit window permits upcoming or ongoing events with verifiable dates. Exclude ended events and candidates without enough date evidence to establish an overlap for a dated request. Test the same timestamp around Seoul midnight under multiple host time zones. For an entirely unusable provider response, return an engine failure with zero credits. A genuinely empty eligible pool returns `no_results` with zero credits.
- Update the app integration test that currently asserts interest is omitted. Verify assignment after deduplication with four disjoint matches, sparse child snapshots, partially usable provider responses and old sessions. The independent reviewer traced the schema and parser limits, job failure handling, app visit-date helper and existing result rendering.

- A shared match anywhere in the eligible inventory selects shared mode, even when it appears after either existing cutoff. A perfect interest match with a closed booking, a disjoint visit date or an incompatible age stays excluded.
- With no shared match, two children with disjoint eligible sets each receive a suitable outing. With three or more children, a result can cover multiple children when verified for each, and the fallback can cover more than three children when needed. A child with no eligible match leaves the other results available. Zero eligible outings produce zero provider calls and zero credit cost.
- Verify KST weekend and next-week boundaries, historical sessions and retries, both final-question branches, and unknown weather, duration, price and transport facts. Use mocked provider responses to verify invalid IDs, partial outputs and exclusion of synthetic private fields from requests, logs and stored errors.
- Replay train and animal preferences on the same eligible pool against the deterministic baseline. Compare top-result fit, unsupported claims, shortlist coverage, token use, p95 latency and timeouts. Report any model evaluation that could not be run. Run the relevant app and server tests, type checks and build. A separate verification agent checks the acceptance criteria after implementation.

### GPT-6.2 Astra review amendments

- Proposed product decision for approval: for dated requests, intersect the requested dates, event dates and the ages allowed for each child. A shared outing needs at least one common eligible day for all selected children. When only part of the window works, give the supported date or range in the reason, respecting any documented operating-day restrictions. In the per-child fallback, apply the same test separately per child. If siblings can attend the same event only on different dates, show each child's applicable date on the single card. Flexible requests use the known upcoming portion of the event interval, including later eligible days after a birthday. Add birthday-crossing fixtures for both age bounds and a case where siblings qualify on different days but never on the same day.
- In OpenAI mode, make one call for a nonempty eligible shortlist. The rule-based engine runs locally. Let the model rank IDs and select from server-provided facts about each candidate. Validate those references and render reasons and cautions in Korean from the verified facts. Test a valid event ID paired with a false free-admission, transit or duration claim and use a factual replacement reason.
- Save the resolved KST start and end as date-only values for new dated sessions. Use these same values for eligibility and history display, including when the device timezone changes. Keep the established device-local calculation for older sessions without a stored range. A per-child fallback uses the original session window. An explicit retry creates a new session and resolves the relative window from its new request time.
- Build the history answer summary from the answers recorded for the session. Render the recorded interest and whichever final question was answered. Support historical atmosphere and place answers. Reopen a saved session after changes to catalog contents and the home address, and verify the displayed answers still describe the original request.
- Capture the selected departure's structured region and locality while the app still has `sido` and `sigungu`. The manual departure answer currently loses the region enum when the address is flattened. Compare region and locality together. Use a same-district boost only when both are known. Test a manual departure in a different region from the saved home and a retry after the saved home changes. Apply the existing Seoul/Gyeonggi broad-region restriction when specified and retain the currently supported event categories, including exhibitions.
- Examine a consistent snapshot of published inventory. The existing list call loads, filters and sorts the whole inventory on every page. Repeated 300-item requests would repeat that work and could skip a shared event if catalog order changed between pages. Prefer one recommendation inventory read that reuses publication rules, then keep only the bounded candidates needed for the model. Verify that reading beyond position 300 does not repeatedly reload the catalogue.

## Implementation verification

The individual fallback validates one pick per covered child and fills omissions deterministically. Repeated event IDs merge their verified attendance details in the card.
- Eligibility requires verifiable start and end dates and at least one documented age bound for requests with children. The completed-month calculation uses calendar days. A birth day that does not exist in the target month reaches its age threshold on the first day of the following month.
- Reuse the existing card and place the conditional visit date and completed ages first in its reasons.
